# ADAPT — an independently written problem bank

OpenOJ's 838 bundles were built by reading LeetCode problems. The
statements, examples, and API names in them are LeetCode's; the judging
data, reference solutions, guides, and figures are ours. This document
designs the program that turns that set into **problems inspired by
LeetCode** — the same computational tasks, the same techniques, the same
difficulty, written independently end to end.

Nothing here has been executed yet. Adapted bundles land in a staging
tree, `openoj-problems/problems-adapt/`, and the live `problems/` tree is
untouched until the whole set passes its gates and we decide to cut over.

## The rule the whole design serves

Treat each source problem as a way to identify a functional
specification, then write everything else from that specification. Never
paraphrase. The working loop per problem is:

1. Read the source bundle.
2. Write down the abstract spec — inputs, output, conditions,
   guarantees, intended technique, intended complexity.
3. Close the source.
4. Write the new problem from the spec alone.

A rewrite that reads like the original with words swapped has failed,
even if every word differs.

## What we hold, and what each artifact needs

Our bundles are not uniform in provenance, so the transformation differs
per file. This table is the contract.

| Artifact | Provenance | Action |
| --- | --- | --- |
| `statement.md` description, examples, constraints | Derived from LeetCode prose | **Rewrite from the spec.** New title, new statement, newly constructed examples, constraints chosen to enforce the intended complexity |
| `statement.md` hints | Ours, but written against their framing | Rewrite from the algorithmic insight |
| `problem.json` `title`, `slug`, `invocation.method`, `class_name`, `entrypoints`, parameter `name`s | LeetCode's public API | **Rename**, consistently across every language |
| `problem.json` `id` | LeetCode's problem number | Replaced by our own sequential id; the mapping lives outside the bundle (see *Provenance ledger*) |
| `problem.json` `difficulty`, `tags` | Ours (our five-level scale, our tags) | Keep; adjust only if the rewrite genuinely shifts the problem |
| `problem.json` `limits`, `comparison`, codecs | Ours (judge configuration) | Keep, unless new constraints change them |
| `cases.json` **public** cases | Mirror the LeetCode examples (check.py enforces 1:1 with statement examples) | **Regenerate** to match the new examples |
| `cases.json` **hidden** cases | Ours — generated by our own reference oracles | Keep where the spec is unchanged; regenerate when constraints move |
| `solution.*` | Ours | Keep the algorithm; rename the API, update comments that name old terminology |
| `starter.*` | Generated by `scripts/gen_starters.py` from `problem.json` | Regenerate — never hand-edit |
| `solutions.md` | Ours | Keep the algorithm exposition; update names, terminology, and any worked example that used the old data |
| `figures/example-*.svg` | Ours, but they **draw the LeetCode examples** | **Redraw for the new examples, or drop.** A figure showing the old numbers is both stale and derived |
| `figures/solution-*.svg` | Ours, illustrate the algorithm | Keep unless the drawing walks through an old example |

The 313 bundles carrying figures are the sharpest trap here: a rewritten
statement with the original example still drawn beside it is worse than
no figure at all.

## Naming

### Titles and slugs

Short, descriptive, algorithm-oriented, searchable. Rename unless the
existing name is an unavoidable generic term (*Binary Search*, *Merge
Sort*). Never rename merely to differ — an awkward title is a worse
outcome than a familiar one.

```
Two Sum                 → Pair Sum                    pair-sum
Valid Parentheses       → Balanced Brackets           balanced-brackets
Maximum Subarray        → Largest Subarray Sum        largest-subarray-sum
Number of Islands       → Count Grid Islands          count-grid-islands
Course Schedule         → Course Dependency Feasibility
Trapping Rain Water     → Trapped Water
```

The directory becomes `<our id>_<new slug>`, keeping check.py's
`<zero-padded id>_<slug>` rule.

### Methods and classes

The public API follows the new title, in every language, including the
entrypoint names for Go, Rust and TypeScript:

```
twoSum → pairSum        (entrypoints: go pairSum, rust pair_sum, typescript pairSum)
isValid → areBracketsBalanced
numIslands → countGridIslands
```

Conventional camelCase where the language expects it; snake_case for
Rust. Do not prepend `solve`/`compute`/`calculate` unless it genuinely
reads better.

The 48 design classes and 2 concurrency classes need class names too —
`LRUCache`, `MinStack`, `Trie`, `MedianFinder`, `H2O` are all LeetCode's:

```
LRUCache → RecencyCache          MinStack → TrackedStack
Trie → PrefixTree                MedianFinder → RunningMedian
H2O → MoleculeAssembler          Codec → TreeSerializer
```

### Oracles

Our nine interactive problems name their oracle after LeetCode's hidden
API — `GridMaster`, `Master`, `MountainArray`, `BinaryMatrix`,
`ArrayReader`, `Robot`, `Sea`, `InfiniteStream`. These are part of the
problem's public surface and get renamed with it:

```
GridMaster → HiddenGrid     MountainArray → PeakedArray
Master → SecretWordOracle   BinaryMatrix → SortedBinaryGrid
ArrayReader → UnboundedReader   Sea → OceanScanner
Robot → CleaningRobot       InfiniteStream → BitStream
```

Renaming an oracle is a **judge change**, not a bundle change: both
harnesses expose the class to submissions by name
(`runner/interactive_oracles.py`, `runner/java/InteractiveOracles.java`,
plus the dispatch tables). The staging tree therefore needs the harness
to accept the new names. Plan: add the new names as the primary ones and
keep the old names as aliases while both trees exist, then drop the
aliases at cutover.

### Parameters

Rename when it improves consistency; keep conventional identifiers
(`nums`, `target`, `root`, `head`, `grid`, `matrix`, `s`, `k`, `n`).
Clarity beats superficial difference. If a parameter is renamed, it
changes in the statement, the skeleton, the type annotations, the
examples, the judge invocation, the fixtures, and the reference
implementation — no stale identifier anywhere.

### SQL problems

Our four SQL bundles carry LeetCode's schema: table names, column names,
and the sample rows in the statement. All three are rewritten — new
table and column names that fit the new framing, new sample data, and
`solution.sql` updated to match. The judge's schema fixtures move with
them.

## Statement style

```
Given <input>, return <output>.
<guarantee or restriction>.
```

Then examples, then constraints. No invented scenarios — no inventory
systems, banks, robots, or kingdoms unless the computation genuinely is
one. A reader should grasp the task as fast as they would a good
interview question.

## Examples

Newly constructed, never permuted from the original. `[2,7,11,15],
target 9` becoming `[7,2,15,11], target 9` is not a new example. Build
2–3 examples that cover meaningfully different shapes (ordinary case, a
negative or empty edge, a duplicate-value case), each small enough to
follow by eye.

Because check.py requires public cases to correspond 1:1 with statement
examples, every new example is also a regenerated public case, with its
expected value computed by the reference solution and asserted.

## Constraints

Rewrite rather than copy. Choose bounds that *enforce* the intended
complexity — if the technique is O(n log n), the bounds must make O(n²)
fail. Check overflow implications when bounds move (a widened value
range can silently require 64-bit accumulation in the C++/Java/Go
ports).

## Guides and hints

Reconstruct from the algorithm, in our existing shape: `## <Approach>`,
the insight, the algorithm, a `**Complexity:**` line. Multi-solution
bundles keep one section per variant, and the section heading must still
resolve to the variant (the matcher pairs them by token containment).

Hints follow the reasoning path — what to notice, what to remember, what
structure makes the lookup cheap — not the answer.

## Layout of the staging tree

```
openoj-problems/
  problems/          # live, untouched during the program
  problems-adapt/    # the adapted set, same bundle format
  .adapt/
    ledger.json      # our id ↔ source id, old/new slug, old/new API
    report/<slug>.md # the per-problem report below
```

The ledger is the one place an old identifier may survive, because
regenerating a bundle needs to know what it came from. It is repository
tooling, not shipped content.

## Verification gates

A bundle is done when all of these pass. Gates 4–6 are the ones that
catch the failures a careful writer still makes.

1. **`scripts/check.py`** — bundle shape, naming, public/example
   correspondence, variant-set parity, formatter cleanliness.
2. **`.localonly/verify_solution.py <key>`** — every solution, every
   variant, every language, N/N.
3. **Sandboxed judge** — submit through the running API. The authoring
   harness applies no limits; this is what caught the concurrency
   failures. Non-negotiable for design, interactive, concurrent and SQL
   bundles.
4. **Cross-solution equivalence** — run the *original* bundle's
   reference solution against the *adapted* bundle's cases (adapting
   only the entry-point name). The algorithm is unchanged by design, so
   it must pass. A failure means the spec drifted during the rewrite.
5. **Stale-identifier scan** — grep the adapted bundle for the old
   title, old slug, old method, old class, old oracle, old parameter
   names, and the old example values. Zero hits.
6. **Prose-overlap scan** — shingle the adapted statement against the
   source statement (7-word n-grams, normalized). Overlap above a small
   threshold means paraphrase rather than rewrite; the problem goes
   back. Common technical phrases (*"return the indices"*, *"in any
   order"*) sit below the threshold naturally and are fine.

Gate 6 is the honest test of whether the rule at the top was followed,
and it is cheap to run.

## Working order

Batch by invocation kind, easiest contract first, so the harness work
lands before the problems that need it:

1. **775 function problems** — the bulk; pure bundle work, no judge
   changes.
2. **4 SQL problems** — schema rewrite.
3. **48 design problems** — class renames.
4. **9 interactive problems** — needs the oracle-alias work first.
5. **2 concurrency problems** — class and method renames, sandbox
   verification.

Within a batch, one problem at a time to completion; no bundle is left
half-consistent. Agents work in slices of ~20–30 bundles, each reporting
per problem:

```markdown
## <source id> — <old title>
- New title / slug:
- Old → new method:
- Core algorithm:
- Difficulty:  (unchanged / adjusted + why)
- Statement rewritten from spec: yes
- Examples newly constructed: yes
- Constraints reviewed: yes
- Skeletons regenerated: <languages>
- Figures: redrawn / dropped / none
- Gates: check.py ✓  verify ✓  sandbox ✓  equivalence ✓  stale-scan ✓  overlap ✓
```

## Decisions to confirm before starting

1. **Cutover.** Does `problems-adapt/` eventually replace `problems/`,
   or do both ship? Replacement is simpler and is what the provenance
   goal implies, but it invalidates every existing submission's slug.
2. **Ids.** Sequential ids of our own (1…838) versus keeping the source
   numbers for continuity. Our own is cleaner; the ledger preserves the
   mapping either way.
3. **Figure budget.** 313 bundles have figures. Redrawing all of them
   for new examples is a large slice of the work; the alternative is
   dropping figures on adapted problems and reintroducing them
   selectively later.
4. **Multi-solution variants.** 42 bundles carry named variants; the
   variant ids (`dijkstra`, `kadane`, `union_find`) are algorithm names,
   not LeetCode's, so they carry over unchanged.
